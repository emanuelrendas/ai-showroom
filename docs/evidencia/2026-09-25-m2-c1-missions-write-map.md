Every surface named in the dispatch was inspected: `app/`, `features/`, `lib/`, server actions, route handlers, RPC wrappers, Supabase client construction, `supabase/migrations/*.sql` (triggers, functions, RPCs), and `tests/` (as fixture setup, classified separately from production-reachable paths).

## Method

1. `grep -rn "from(\"missions\")\|from('missions')\|\.missions\b"` across `app/`, `features/`, `lib/` — locates every Supabase-js query builder call against the table.
2. `grep -rn "\.insert(\|\.update(\|\.delete(\|\.upsert(\|rpc("` across `app/`, `features/`, `lib/` — locates every mutation-shaped call anywhere in application code, independent of table name, then each hit was read in full context and classified by target table.
3. `grep -n "missions"` across every file in `supabase/migrations/*.sql` — locates every SQL-level reference (table DDL, triggers, functions, RPCs, RLS policy predicates) to confirm no function or trigger mutates `missions` outside the touch-updated-at trigger.
4. Full read of `lib/supabase/server.ts` and `lib/supabase/client.ts` — establishes the credential/context every one of the above calls actually runs under.
5. Full read of `features/ai/actions.ts`, `generate-mission-ai-draft.ts`, `mission-ai-draft-writer.ts`, `draft-mutations.ts`, `inference-log-supabase-adapter.ts` — the entire M2 AI generation/review/approval call chain, traced end to end.
6. Full read of `tests/rls/mission-ai-drafts.rls.test.ts` — the only place a `missions` INSERT appears outside `features/missions/actions.ts`, to confirm it is test-fixture setup, not a reachable production path.

**No other write path exists.** Specifically, confirmed absent:

- **No UPDATE path.** `public.missions` has an `UPDATE` RLS policy (`missions_update_member`, `supabase/migrations/20260901151420_milestone_1_foundation.sql:357-374`) and an explicit `grant ... update ... on public.missions to authenticated` (line 498 of the same file) — the database *permits* a workspace member to update a mission's own columns, as ordinary CRUD infrastructure. But **no application code anywhere calls `.from("missions").update(...)` or `.from("missions").upsert(...)`.** There is no Server Action, route handler, or UI control in this repository that edits an existing Mission's `status`, `title`, `description`, or `priority` after creation. The DB-level permission exists; the application-level call that would exercise it does not.
- **No DELETE path.** Same pattern: `missions_delete_member` policy and a `delete` grant exist at the database level (Milestone 1 infrastructure), but no application code anywhere calls `.from("missions").delete(...)`.
- **No RPC writes to `missions`.** Every RPC defined in `supabase/migrations/*.sql` was inspected in full:
  - `public.create_workspace_with_owner(text, text)` (`20260901151420_milestone_1_foundation.sql:455-491`, redefined `20260901165904_fix_workspace_bootstrap_rls.sql:1-36`) — writes only to `public.workspaces` and `public.workspace_members`. Never references `missions`.
  - `public.approve_mission_ai_draft(uuid)` (`20260922140000_create_mission_ai_drafts.sql:91-132`) — writes only to `public.mission_ai_drafts` (`status`, `approved_by`, `approved_at`). Its only read of `missions` is transitively via the `mission_ai_drafts.mission_id` foreign key at row-fetch time; it issues zero DML against `public.missions`.
  - `private.handle_new_user()`, `private.touch_updated_at()`, `private.enforce_mission_ai_draft_hitl_gate()`, `private.reject_inference_logs_mutation()`, `private.inference_logs_ensure_partition(date)`, the RLS auto-enable event-trigger stubs — none reference `public.missions` at all except the `missions_touch_updated_at` trigger, which only stamps `updated_at = now()` on whatever UPDATE reaches the row (it does not itself initiate a write; it fires only if some other statement already issued one, and no such statement exists in application code, per above).
- **No AI/server-originated write of any kind.** The complete M2 AI call chain — `generateMissionAiDraftAction` (`features/ai/actions.ts:20-90`) → `generateMissionAiDraft` (`features/ai/generate-mission-ai-draft.ts:32-51`) → `InferenceExecutionWrapper.execute` (persists to `inference_logs` only) → `SupabaseMissionAiDraftWriter.write` (`features/ai/mission-ai-draft-writer.ts:26-48`, inserts to `mission_ai_drafts` only) — was traced end to end. It calls `getMissionById` (`features/missions/queries.ts:18-31`, a `SELECT`, read-only) once, to validate the mission exists and belongs to the given project/workspace before generating. **It never calls `.from("missions")` with `.insert()`, `.update()`, `.delete()`, or `.upsert()`, and never calls an RPC that does.** The model's structured output (`SingleModelOutput`: `summary`, `suggested_actions`, `confidence_score`, `confidence_tier`) is written exclusively into `mission_ai_drafts` columns; none of it is ever written into any `missions` column.
- **No service-role usage in application code.** `grep -rn "service_role\|SUPABASE_SERVICE_ROLE"` across the entire repository (excluding `node_modules`) returns exactly one hit, in `tests/unit/obsidian-sync-isolation-policy.test.ts:356`, a string literal naming an unrelated `raioc-os` environment-variable key inside an Obsidian-sync isolation test — not a Supabase client construction, and not reachable from any M2 code path. `lib/supabase/server.ts` and `lib/supabase/client.ts` (the only two places a Supabase client is constructed in application code) both use the **publishable key** exclusively. The only place the **secret/service-role key** is used at all is `tests/rls/*.test.ts`, as the `admin` client used to prove RLS/trigger boundaries hold even against an elevated role — test-only, never part of a runtime request path, and not reachable by an end user or the AI generation flow.
- **`missions` INSERT inside `tests/rls/mission-ai-drafts.rls.test.ts:156-175`** — this is `beforeAll` fixture setup, using `ownerClient` (a real signed-in `authenticated`-role client created via `signInWithPassword`, the same credential class as row 1 above), to create a Mission the test's `mission_ai_drafts` rows can legitimately reference. It exercises the same single production INSERT path (`missions_insert_member` policy), not a second path — it is test scaffolding, not new code.

## Conclusion

There is exactly **one** write path to `public.missions` in this codebase: Mission creation, gated by `missions_insert_member` RLS and a real authenticated human session, entirely outside the AI generation/review/approval flow. The AI/server execution boundary — the `authenticated`-role, session-bound Supabase client used by `generateMissionAiDraftAction` and everything it calls — issues **zero** `INSERT`, `UPDATE`, `DELETE`, `UPSERT`, or RPC-write calls against `public.missions` anywhere in this repository. This conclusion is evidence-based: every `.insert(`, `.update(`, `.delete(`, `.upsert(`, and `rpc(` call in `app/`, `features/`, and `lib/` was individually read and classified (table above and "No other write path exists" section), and every SQL function/trigger/RPC in `supabase/migrations/` was individually read for any DML against `missions`.

This directly informs **C2**: the real, reachable AI/server credential boundary to test is the `authenticated` Postgres role as exercised by the M2 generation/review/approval call chain — the same client construction as row 1 above (`lib/supabase/server.ts`, publishable key, session-bound). There is no separate "AI role" or "service context" in this architecture to invent a test for; C1 has already shown the actual AI/server code path never attempts a `missions` mutation. C2's job is therefore to prove, against that same real `authenticated` boundary and independent of what application code happens to call today, that the database itself would refuse an attacker or a future regression that *did* attempt to fabricate an AI-approved state through the `mission_ai_drafts` boundary Option B actually relies on — see `docs/evidencia/2026-09-25-m2-c2-missions-mutation-proof.md`.
